## 5. Decisions Made

1. **Semantic color tokens, not inline dark mode checks** — The approach is `values/colors.xml` (light) + `values-night/colors.xml` (dark). Android resolves the correct file automatically at runtime. No `if (isDarkMode)` checks in code, no in-app toggle needed. All existing callers that used `@color/xxx` in XML switch for free.

2. **Custom View colors as `get()` properties** — `CycleProgressRingView`, `CycleCalendarView`, `SheetCalendarView` draw to Canvas with `Paint` objects. `@color` references in XML don't reach Paint. Kotlin `get()` property calls `context.getColor(R.color.xxx)` on every draw, so live dark mode switching updates the canvas without requiring a full view recreate.

3. **Brand and medical colors kept hardcoded** — `#EC4899` (period pink), `#A855F7` (fertile purple), `#C2185B` (ovulation red), `#3B7A57` (fertile green) have semantic clinical meaning. They must look the same in both modes. Tokenizing them would allow accidental dark-mode overrides by future developers.

4. **PDF export colors kept hardcoded** — PDF is always rendered on a white page regardless of system theme. Token colors would pull dark values into a white-background PDF.

5. **Unused resource cleanup** — 15 drawables, 4 layouts, 3 color selectors deleted. No reference to any of them was found in Kotlin or XML after scanning the full source tree. Deletion reduces APK size and build time.

6. **`futurePeriodDays(monthsAhead=3)` instead of single prediction** — Users with irregular cycles need to see at least 3 predicted periods on the calendar to understand their pattern. Returning only the next period made the calendar look empty after the first pink block.
