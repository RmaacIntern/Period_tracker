**DB rename strategy detail:**
Room migrations run *inside* an already-open database connection — they cannot rename the file that is currently open. The correct approach is:

```kotlin
// In MainApplication.onCreate(), BEFORE AppDatabase.getInstance() is ever called:
val oldFile = getDatabasePath("lunacycle.db")
val newFile = getDatabasePath("period_tracker.db")
if (oldFile.exists() && !newFile.exists()) {
    oldFile.renameTo(newFile)
}
```

This runs once on the first launch after the update. If the old file exists and the new one doesn't, it is renamed. After this, `Room.databaseBuilder(context, AppDatabase::class.java, "period_tracker.db")` opens the renamed file and runs MIGRATION_6_7 (which is a no-op schema migration — it exists only to bump the version so Room's schema hash check passes on the renamed file).

## 4. Decisions Made

1. **Package name: `com.aivigil.periodtracker`** — This is the production package name for the Play Store listing under the Aivigil company account. The old `com.example.` prefix is a development placeholder that Play Store rejects. Once an app is published with a package name it can never be changed — any change creates a completely different app in Play Store with zero user history, reviews, or install count. Choosing the right name now, before publishing, is critical.

2. **How the package rename was done** — Android Studio's built-in **Refactor → Rename** was used on the root package directory. This updated every `package` declaration, every `import` statement, the `namespace` and `applicationId` in `build.gradle.kts`, and the FileProvider `authorities` string in the manifest. The rename was done in a single refactor operation to avoid missing any file.

3. **`google-services.json` must be re-downloaded after package rename** — Firebase identifies your app by its package name (called "App ID" in the Firebase Console). The old `google-services.json` was registered against `com.example.periodtracker`. After the rename, a new Android app entry with package `com.aivigil.periodtracker` was added to the Firebase project, and a new `google-services.json` was downloaded and replaced in `app/`. Without this step, Firebase initialisation would fail silently.

4. **DB rename via pre-open file rename, not a Room migration** — Room migrations execute SQL inside an already-open database connection. A migration object cannot rename the file that is currently open. The solution is to rename the file at the OS level in `MainApplication.onCreate()`, before any code calls `AppDatabase.getInstance()`. The migration `MIGRATION_6_7` exists as a no-op (or minimal structural change) purely to increment the version number, because Room validates the version chain on every open. An existing device with DB version 6 running the new build gets: file rename (Application.onCreate) → Room opens `period_tracker.db` → runs MIGRATION_6_7 → version becomes 7 → normal operation.

5. **Native ad: no `MediaView`** — The `NativeAdView` layout deliberately omits a `MediaView`. The Google Next-Gen SDK documentation states: "If you prefer to render your native ad without a MediaView instance, pass null for the media view parameter when calling `registerNativeAd()`." A `MediaView` smaller than 120dp × 120dp triggers a validator warning ("MediaView is too small for video") and video creatives won't serve to it anyway. Since the app's card layout does not have space for a large media view, omitting it entirely is cleaner than shrinking one to an invalid size.

6. **Native ad CTA button: Material tint cleared before gradient applied** — `AppCompatButton` inherits a Material colour tint from the app theme that overrides `android:background`. Simply setting a `GradientDrawable` as the background has no visible effect because the tint is drawn on top. The fix: call `callToAction.backgroundTintList = null` first, then set the `GradientDrawable`. The gradient uses slightly darker brand colours (`#D63384`, `#9333EA`) instead of the standard `#EC4899`/`#A855F7` to visually distinguish the ad CTA from the app's own buttons.

7. **Native ad `advertiser` field: kept in layout, hidden by default** — The `adAdvertiser` view exists in `layout_native_ad.xml` and is registered with `adView.advertiserView = advertiser`, but `visibility = View.GONE`. It must be registered for AdMob policy compliance (the SDK uses registered view IDs for click attribution) but it is hidden because the design has no visible space for it.

8. **`isLoading` flag prevents duplicate native ad requests** — Without this guard, rapidly switching fragments or rotating the screen could trigger multiple simultaneous `NativeAdLoader.load()` calls. Only one can succeed, but the extra requests waste quota. The flag is reset in both `onNativeAdLoaded` and `onAdFailedToLoad` callbacks.
