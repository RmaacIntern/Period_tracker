## 4. Decisions Made

1. **App name changed from LunaCycle to Period Tracker** — Team lead instruction. Applied to `strings.xml`, splash, onboarding screens. Package name (`com.example.lunacycle`) not yet changed — that is a more disruptive refactor tracked separately.

2. **Prediction logic completely replaced — averaged/signal-based → user-setting-based.** This is the biggest architectural decision of the project. Full reasoning below:

   **What the old system did:**
   The old `bestPrediction()` ran a weighted average of the last 6 confirmed cycle lengths. It also detected ovulation signals — BBT thermal shift (3-day rule), cervical fluid progression (egg white → next day), and LH surge — and used a hierarchy (BBT takes priority over cervical over formula) to predict the ovulation date. Every time a new period was confirmed, `logPeriodStart()` automatically recalculated the cycle length average and silently overwrote the user's setting with the computed result.

   **Why it caused real problems:**
   - A user who set their cycle length to 35 days in Profile would find that after a few logged cycles the prediction shifted to 29 days (the average) with no explanation why. The user's explicit setting was ignored.
   - The ovulation alarm was firing on dates that had already passed — the signal hierarchy was computing ovulation dates in the past on every prediction refresh, and the alarm was being rescheduled for those past dates (discovered as a separate alarm bug this session).
   - The confidence score (10–95%) was shown to users but there was no way to explain what it meant or how to improve it. A user with 3 confirmed cycles got 40% confidence; they had no way to know why it wasn't higher.
   - The system was harder to debug: a wrong prediction could be caused by bad BBT data, unusual cervical readings, a data entry error, or the averaging algorithm — four different sources to check.

   **What the new system does:**
   - `nextPeriod = lastPeriodStart + cycleLength` (the value the user set in Profile, never overwritten)
   - `ovulation = nextPeriod − 14` (fixed luteal phase — biologically correct; the luteal phase is consistently 14 days across most women; it's the follicular phase that varies)
   - `fertileStart = ovulation − 5`, `fertileEnd = ovulation + 1`
   - BBT, LH, and cervical fluid are still logged and shown to the user for their own reference — they are not deleted, just not used for predictions
   - Confidence fixed at 85%, label is "Based on your data"

   **Why this is the right decision for this app:**
   The app is a consumer period tracker, not a clinical fertility monitor. The primary use case is "tell me when my next period is." A user who says "my cycle is 28 days" expects to be told "in 28 days." The signal-based system was solving a different problem (precision fertility prediction) and introducing bugs into the simpler problem. Signals can be a future ML feature when there is enough data to train on — not an MVP feature.

3. **`PeriodConfirmReceiver` critical fix** — The notification "Yes, started" action was inserting a raw `PeriodEntry` directly into the DAO, bypassing `CycleRepository.logPeriodStart()`. This meant that when a user confirmed their period from a notification, the previous period was never closed, cycle length was never calculated, and predictions were never refreshed. The correct call is through the repository, not the DAO.

4. **Dialog trigger tightened** — The period start dialog now only fires when all 3 conditions are true: today's date, new entry (not editing), and flow is Light/Medium/Heavy. Spotting is explicitly excluded because spotting is not the start of a period biologically. Past date edits are excluded because you cannot start a period "today" if the log date is in the past.

5. **Notification permission on Profile switches (Android 13+)** — A switch that appears to turn on reminders but silently does nothing because `POST_NOTIFICATIONS` permission was not granted is worse than showing no switch at all. The `withNotifPermission()` helper makes the permission flow explicit.
